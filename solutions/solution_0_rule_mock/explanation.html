What Solution 0 Is

Think of it as the first working scoreboard. It is not trying to win yet. It makes the problem runnable, measurable, and explainable.

Task 1

Autocomplete for process steps

For a partial process route, the n-gram model ranks the five most likely next steps. This is like code autocomplete, except the tokens are semiconductor manufacturing steps instead of Python keywords.

Task 2

Continue the remaining route

It repeatedly predicts one next step until it reaches SHIP LOT, an end marker, or a repeated context. This gives a full predicted suffix after the provided cut point.

Task 3

Rule-check anomaly detection

It calls the public validator from training_data/generate_sequences.py. That is why this part is called a mock or oracle: it uses the known rules directly instead of learning them from examples.

Honest naming: I chose solution_0_rule_mock instead of solution_0_stupid. The solution is simple, but it is not random. It understands the official task shapes, reads the provided data, writes measurable outputs, and makes the judging gaps visible. "Rule mock" is more precise because Task 3 is deliberately solved with a rule oracle.

Beginner Primer: The Words We Keep Using

This section is for a junior teammate who has never built a sequence model. The rest of the report becomes much easier once these ideas are clear.

Vocabulary

Step

A step is one named manufacturing operation, such as HF DIP, DEPOSIT PASSIVATION, or WAFER SORT TEST.

In normal NLP, a model predicts words. In this track, the model predicts process steps.

Vocabulary

Token

A token is the atomic item the model sees. Here, each full process step string is treated as one token.

That means DEPOSIT BACKSIDE METAL is one token, not three word tokens.

Vocabulary

Sequence

A sequence is an ordered list of tokens. One wafer-lot route might be 120 to 150 steps long.

The order is the point. SHIP LOT is valid near the end, but invalid before testing.

Input shape

Prefix / partial sequence

A prefix is the part of the route we are allowed to see. If the full route has 120 steps and the eval cuts it at 60%, the prefix contains about 72 steps.

The model must infer what comes next using only that visible prefix.

Target shape

Suffix / remainder

The suffix is the hidden part after the cut point. For Task 2, we predict the suffix only.

We do not repeat the prefix in completion.csv, because the official docs say to predict only the steps after the cut point.

Modeling

Baseline

A baseline is the simple method everyone should beat. It tells us whether a fancy model is actually useful.

If a transformer only ties this baseline, then the expensive model is not giving us a convincing win.

The big one

What is an n-gram model?

An n-gram model is a counting model for sequences. It does not have neural network layers, embeddings, attention heads, or GPU training. It simply counts what usually follows a short recent history.

The "n" tells us how many tokens are in the pattern. A 2-gram, also called a bigram, looks at one previous token plus the next token. A 3-gram, also called a trigram, looks at two previous tokens plus the next token. In Solution 0, n=3, so the model mostly asks: "given the last two steps I saw, what step most often followed those two steps in training?"

Tiny made-up counting example

Suppose the training data contains these local patterns:

CURE PASSIVATION -> MEASURE PASSIVATION THICKNESS -> OPEN PAD WINDOW
CURE PASSIVATION -> MEASURE PASSIVATION THICKNESS -> OPEN PAD WINDOW
CURE PASSIVATION -> MEASURE PASSIVATION THICKNESS -> MEASURE PASSIVATION QUALITY

If the visible prefix ends with CURE PASSIVATION | MEASURE PASSIVATION THICKNESS, the trigram model has counted that OPEN PAD WINDOW followed this context twice and MEASURE PASSIVATION QUALITY followed it once. So it ranks OPEN PAD WINDOW higher.

Why it works at all

Industrial routes have repeated local structure

Semiconductor process flows are not random text. Many local chunks repeat: lithography often has coat, bake, align, expose, develop; etch is often followed by strip and clean; test happens near the end. Counting those chunks already gives a surprisingly useful signal.

Why it fails

Local memory is not process understanding

A trigram can know what usually follows the last two steps, but it does not truly know which lithography level it is in, whether the route already passed passivation, or whether it is globally near the end. Long routes need longer-range state and constraints. 

class NGramModel:
    def __init__(self, n: int = 3, alpha: float = 0.4):
        self.n = n
        self.alpha = alpha
        # counts[order][context_tuple][token] -> count ; order 0 == unigram
        self.counts: list[dict] = [defaultdict(Counter) for _ in range(n)]
        self.vocab: set[str] = set()
        self.total: int = 0

    def fit(self, sequences):
        for seq in sequences:
            s = ["<bos>"] + list(seq) + ["<eos>"]
            self.vocab.update(s)
            for i, tok in enumerate(s):
                self.total += 1
                for order in range(self.n):
                    if i - order < 0:
                        break
                    ctx = tuple(s[i - order:i])
                    self.counts[order][ctx][tok] += 1
        return self
<bos> and <eos>

These are special markers. <bos> means "beginning of sequence" and <eos> means "end of sequence." They help the model learn what usually starts and ends a route.

self.vocab

The vocabulary is the set of all step tokens the model has seen. The model can only rank tokens from this vocabulary.

context_tuple

The context is the recent history. For a trigram, the most specific context has two previous tokens.

Counter

A Python Counter stores counts like "after this context, this next token appeared 37 times."

Backoff and alpha

What happens when the exact recent history was never seen?

Sometimes the model sees a context in eval that never appeared in training. If the exact last-two-step context was unseen, the model backs off to a shorter context. In plain English: "I do not know what follows these exact two previous steps, so I will look only at the previous one step. If that still fails, I will look at overall step frequency."

The alpha=0.4 value is a discount for backed-off guesses. A prediction from an exact two-step context should be trusted more than a prediction from a weaker one-step or zero-step context.

How the Self-Eval Set Is Built

The goal is to imitate the official shape closely enough that future solutions can be compared without waiting for hidden organizer files.

Load every sequence source

The loader scans training_data/*.csv, detects the product family from the file name, parses long-format sequences when possible, and falls back to one canonical sequence from STEP-only files.

Validate the loaded sequences

Every sequence is passed through validate_sequence(). The inventory records how many valid and invalid sequences each source contains. In the current provided data, all loaded sequences are valid.

Hold out 100 long-format sequences per family

That gives 300 held-out complete routes across MOSFET, IGBT, and IC. Only long-format generated variants are held out, so canonical reference routes can still help the baseline learn structure.

Create two valid partial examples from each held-out route

Each route is cut at 60% and 80%, matching the official eval_input_valid.csv design. That creates 600 examples for Task 1 and Task 2.

Create anomaly examples

For each held-out route, Solution 0 keeps one valid copy and creates one invalid copy by moving or deleting steps until the public validator confirms a rule violation. That creates 600 anomaly rows.

def load_split() -> tuple[
    dict[str, list[str]],
    dict[str, dict[str, list[str]]],
    list[dict[str, object]],
    dict[str, dict[str, SequenceRecord]],
]:
    """Return train sequences and held-out self-eval sequences per family."""
    rng = random.Random(SEED)
    train: dict[str, list[str]] = {}
    heldout: dict[str, dict[str, list[str]]] = {}
    by_family, inventory = load_all_available_sequences()

    for family in FAMILIES:
        records = by_family[family]
        eval_candidates = [
            key for key, record in records.items()
            if record.source_kind == "long_format_sequence"
        ]
        rng.shuffle(eval_candidates)
        eval_keys = set(eval_candidates[:EVAL_PER_FAMILY])

        keys = sorted(records)
        heldout[family] = {
            key: records[key].steps
            for key in keys
            if key in eval_keys
        }
        for key in keys:
            if key not in eval_keys:
                train[key] = records[key].steps

    return train, heldout, inventory, by_family
random.Random(SEED)

This makes the held-out sample deterministic. If you rerun the script, you get the same split.

record.source_kind == "long_format_sequence"

The self-eval set comes from generated multi-sequence files, not from single canonical reference files.

EVAL_PER_FAMILY

This constant is 100. With three families, that creates 300 complete held-out routes.

train[key] = records[key].steps

Everything not held out becomes training data. That is how we get 6709 training sequences.

Task 1 code path

Next-step prediction: ask the n-gram model for five candidates

An n-gram model counts local step patterns. With n=3, it mainly looks at the last two steps in the prefix, then asks: "after this two-step context, what usually came next in training?" 

def predict_task1(model: NGramModel, examples: list[ValidExample]) -> list[dict[str, object]]:
    rows: list[dict[str, object]] = []
    for ex in examples:
        ranks = model.next_step_ranking(ex.partial, k=5)
        ranks = ranks + [""] * (5 - len(ranks))
        rows.append(
            {
                "EXAMPLE_ID": ex.example_id,
                "RANK_1": ranks[0],
                "RANK_2": ranks[1],
                "RANK_3": ranks[2],
                "RANK_4": ranks[3],
                "RANK_5": ranks[4],
            }
        )
    return rows
model.next_step_ranking(ex.partial, k=5)

This is the actual prediction. The model gets the visible partial route and returns its top five next-step guesses.

ranks + [""] * ...

The official file needs exactly five rank columns. If the model somehow returns fewer than five candidates, blanks fill the missing columns.

RANK_1 through RANK_5

These column names match the official submission format from generation_rules.md.

Task 2 code path

Sequence completion: repeatedly predict one step

Completion is harder than Task 1 because one early mistake changes the prefix for every later prediction. This is why the same model can have perfect Top-5 next-step accuracy but still weak full-sequence completion. 

def rollout_completion(model: NGramModel, prefix: list[str], max_new_steps: int) -> list[str]:
    """Greedy n-gram rollout with simple loop prevention.

    The base n-gram can get trapped in repeating lithography cycles. That is a
    real baseline limitation, but the submission file should still stay bounded.
    """
    seq = list(prefix)
    predicted: list[str] = []
    seen_contexts: set[tuple[str, ...]] = set()
    context_width = max(1, model.n - 1)

    for _ in range(max_new_steps):
        context = tuple(seq[-context_width:])
        if context in seen_contexts:
            break
        seen_contexts.add(context)

        nxt = model.next_step_ranking(seq, k=1)[0]
        if nxt == "<eos>" or nxt == seq[-1]:
            break
        predicted.append(nxt)
        seq.append(nxt)
        if nxt == "SHIP LOT":
            break
    return predicted
seq = list(prefix)

The model starts from the partial route the eval input gives us.

seen_contexts

This prevents infinite loops. Semiconductor routes revisit similar lithography and etch patterns, so a simple local model can get stuck repeating itself.

model.next_step_ranking(seq, k=1)[0]

The rollout is greedy: it always takes the single most likely next step, appends it, and predicts again.

SHIP LOT

This is a natural stopping point. Once the lot ships, there should be no more manufacturing steps.

Task 3 code path

Anomaly detection: use the public rule validator as an oracle

This is the most important honesty point in Solution 0. The code does not learn anomaly detection. It directly calls the rule checker that the repo provides. That creates a strong format baseline and a perfect local oracle, but it is not evidence of learned process understanding. 

def predict_task3(examples: list[AnomalyExample]) -> list[dict[str, object]]:
    rows: list[dict[str, object]] = []
    for ex in examples:
        violations = validate_sequence(ex.sequence)
        is_valid = 0 if violations else 1
        rows.append(
            {
                "EXAMPLE_ID": ex.example_id,
                "IS_VALID": is_valid,
                "SCORE": 1.0 if is_valid else 0.0,
                "PREDICTED_RULE": "" if is_valid else violations[0].rule,
            }
        )
    return rows
validate_sequence(ex.sequence)

This function comes from training_data/generate_sequences.py. It returns a list of rule violations found in the sequence.

is_valid = 0 if violations else 1

The official format uses 1 for valid and 0 for invalid. This line maps the validator result to that format.

SCORE

This is a valid-probability score. The oracle is totally confident, so valid sequences get 1.0 and invalid sequences get 0.0.

PREDICTED_RULE

When invalid, the first validator rule ID is written out. That supports rule attribution accuracy.

Exactly What Goes Into Each CSV

The jury does not read Python objects. They receive CSV files. This section explains the three output files slowly, because format mistakes are one of the easiest ways to lose points.

Task 1

nextstep.csv

One row per partial route. The row contains the example ID and five ranked guesses. RANK_1 is the model's favorite answer. RANK_5 is still a guess, but lower confidence.

Task 2

completion.csv

One row per same partial route. The model writes the remaining steps as one pipe-separated string. The pipe character | is just a separator between step names.

Task 3

anomaly.csv

One row per full route. The model says whether the route is valid, gives a validity score, and optionally names the rule that was broken.

Sample shape

EXAMPLE_ID,RANK_1,RANK_2,RANK_3,RANK_4,RANK_5

This means: for valid_0001, the model thinks MEASURE FILM THICKNESS is the most likely next step. If the ground truth next step is in any rank position, Top-5 gets credit. If it is exactly RANK_1, Top-1 gets credit.

Why this matters for future solutions: a later transformer, beam-search decoder, or learned anomaly detector can replace the prediction logic, but it should keep the same CSV contract. That lets us compare Solution 1 against Solution 0 without rewriting the scoring harness.

The 10 Forbidden Rules in Plain English

Task 3 is about detecting process-logic violations. Solution 0 uses the public validator directly, so it can catch these rules perfectly on our local generated anomalies. A final learned model should show it can discover or approximate these rules without simply calling the oracle at inference time.

Rule ID Plain-English meaning Why it matters Example of the bad pattern
RULE_DEP_NO_CLEAN A deposition step needs a recent cleaning or surface-prep step before it. You do not want to deposit material onto a dirty or unprepared surface. ETCH VIA -> DEPOSIT BARRIER METAL with no clean in between.
RULE_METAL_ETCH_NO_LITHO A metal etch needs a completed lithography pattern before it. Etching metal without a pattern means the process has no mask defining where to etch. DEPOSIT METAL 1 -> ANNEAL METAL 1 -> METAL ETCH.
RULE_ETCH_NO_MASK Most etch steps need a recent develop step from lithography. The developed resist pattern tells the etch where material should be removed. MEASURE OXIDE THICKNESS -> OXIDE ETCH.
RULE_LITHO_LEVEL_SKIP Lithography mask levels must appear in sequence. Do not jump to level 3 before level 2 is complete. Layer ordering matters; skipping a mask level breaks the process route. ALIGN MASK LEVEL 3 appears before ALIGN MASK LEVEL 2.
RULE_IMPLANT_NO_MASK Implant steps need an opened region from oxide etch or lithography. Implanting dopants requires the correct region to be exposed. MEASURE JUNCTION DEPTH -> IMPLANT LDD.
RULE_CMP_NO_DEP CMP needs a recent deposition or fill step before it. CMP planarizes material. If nothing was deposited or filled, CMP does not make process sense. MEASURE PLANARITY -> CMP METAL.
RULE_PAD_OPEN_BEFORE_DEP Pad windows should open only after passivation has been deposited and cured. The pad opening is part of the passivation/bond-pad flow and should not happen before the protective layer exists. OPEN PAD WINDOW -> DEPOSIT PASSIVATION.
RULE_TEST_BEFORE_PASSIVATION Electrical tests should happen after passivation cure. The device should pass through the protective passivation stage before final electrical testing. DEPOSIT PASSIVATION -> PARAMETRIC TEST -> CURE PASSIVATION.
RULE_SHIP_BEFORE_TEST SHIP LOT must not happen before WAFER SORT TEST. You do not ship the lot before mandatory wafer sort testing. SHIP LOT -> WAFER SORT TEST.
RULE_BACKSIDE_BEFORE_PASSIVATION Backside metal deposition must happen after passivation cure. The frontside should be protected before backside metallization. DEPOSIT BACKSIDE METAL -> DEPOSIT PASSIVATION.
Why Task 3 is perfect for Solution 0: the validator already knows these rules exactly. That is useful for creating a labeled local test set and validating CSV format, but it is not the final winning claim. The final claim should be: "our trained model learned signals that line up with these rules, and we can show where the sequence becomes suspicious."

Metric Glossary, Explained Like We Are New to This

These are the judging words from the track docs. A metric is just a rule for converting predictions into a number. Different metrics reward different behavior.

Task 1

Top-1 Accuracy

Top-1 asks: "Was the model's first guess exactly the true next step?"

Top-1 = correct first guesses / number of examples

Our value is 0.6800, so 68% of first guesses are correct on local self-eval.

Task 1

Top-3 and Top-5 Accuracy

Top-3 asks whether the true step appears anywhere in the first three guesses. Top-5 asks whether it appears anywhere in the first five guesses.

These metrics are friendlier than Top-1 because the model can get credit for ranking the right answer as plausible, even if it was not the first choice.

Our Top-5 is 1.0000, which means the true next step always appears somewhere in the five guesses locally.

Task 1

MRR

MRR means Mean Reciprocal Rank. It rewards the true answer appearing higher in the ranked list.

If the answer is rank 1, the score for that example is 1/1 = 1.0. If it is rank 2, the score is 1/2 = 0.5. If it is rank 5, the score is 1/5 = 0.2. Then we average across examples.

Our MRR is 0.8336, which is consistent with many true answers appearing near the top.

Task 2

Exact Match Rate

Exact match is strict. The predicted remainder must equal the true remainder step-for-step, with no missing steps, no extra steps, and no wrong order.

This is very hard for long sequences. One early mistake makes the whole suffix non-exact.

Our exact match is 0.0000, which means Solution 0 never predicts the entire hidden suffix perfectly.

Task 2

Normalized Edit Distance

Edit distance counts how many insertions, deletions, or substitutions are needed to turn the prediction into the true answer.

"Normalized" means divided by sequence length so examples of different lengths can be compared. Lower is better.

Our value is 0.6152, which is not good. It says the predicted suffixes are far from exact.

Task 2

Token Accuracy

Token accuracy compares predicted and true suffixes position by position.

If the true step at position 10 is VIA ETCH and the predicted step at position 10 is also VIA ETCH, that position gets credit.

Our value is 0.2073, so about 20.7% of exact step positions match.

Task 2

Block-Level Accuracy

Block-level accuracy is a softer version of token accuracy. Instead of asking whether the exact step name matches, it asks whether the coarse process category matches.

For example, two different measurement steps may both count as "inspection/measurement" even if the exact names differ.

Our value is 0.3922, which is better than token accuracy but still weak.

Task 3

Binary Accuracy

Binary accuracy asks whether we got the valid/invalid label right.

There are only two labels: valid or invalid. In the CSV, valid is 1 and invalid is 0.

Our value is 1.0000 because the rule oracle directly checks validity.

Task 3

Precision and Recall

Precision asks: "When we predicted valid, how often were we right?" Recall asks: "Of all truly valid sequences, how many did we catch as valid?"

These matter when one class is rarer or more costly than the other. For example, falsely accepting an invalid process route could be worse than falsely flagging a valid route for review.

Task 3

F1

F1 combines precision and recall into one number. It is useful when we care about both false alarms and missed detections.

F1 = 2 * precision * recall / (precision + recall)

Our F1 is 1.0000 locally because the oracle makes no valid/invalid mistakes on the generated self-eval anomalies.

Task 3

Confusion Matrix

A confusion matrix is a small table of the four possible valid/invalid outcomes.

TP means a valid sequence predicted valid. TN means an invalid sequence predicted invalid. FP means invalid accepted as valid. FN means valid rejected as invalid.

For this run: TP=300, TN=300, FP=0, FN=0.

Task 3

ROC-AUC

ROC-AUC evaluates the ranking quality of a score, not just a hard valid/invalid label.

If every valid sequence receives a higher validity score than every invalid sequence, AUC is 1.0. If scores are random, AUC is around 0.5.

Our AUC is 1.0000 because the oracle gives valid rows 1.0 and invalid rows 0.0.

Task 3

Rule Attribution Accuracy

Detecting "invalid" is not the whole job. Rule attribution asks whether we can name the broken rule, such as RULE_SHIP_BEFORE_TEST or RULE_CMP_NO_DEP.

This is valuable for a human engineer because "invalid" alone does not say what to fix.

Task 4

OOD Generalization

OOD means out-of-distribution. In this track, the organizers will test on an undisclosed fourth product family after submission.

The danger is memorizing MOSFET, IGBT, and IC route patterns without learning reusable process logic. Our local proxy trains on two families and tests on the third.

Task 4

Performance Drop

Performance drop means the difference between in-distribution performance and OOD performance.

If a model gets 95% Top-1 on known families but only 55% on a hidden family, the drop is large. A winning model should keep the drop as small as possible.

Junior-engineer takeaway: do not optimize only the headline number that looks best. Solution 0 looks excellent on Task 1 Top-5 and Task 3 oracle metrics, but Task 2 shows that it does not truly generate long routes well. The final pitch should use multiple metrics to tell an honest story.

Connection to "When Will This Lot Finish?"

The reference page made this distinction clear: predicting the next process step and forecasting finish time are related, but they are not the same product.

What Solution 0 can do

Estimate the remaining route shape

Task 2 produces a predicted list of remaining steps. That answers: "what operations might still be ahead after this partial trace?"

What it cannot do yet

Predict calendar time

Finish time needs more than step names. We would need step durations, queue state, tool availability, maintenance windows, dispatch rules, WIP, holds, sampling decisions, and maybe rework probability.

How this becomes useful

Route model + scheduling model

A stronger system could first predict or validate the remaining route, then feed those remaining operations into a scheduling/forecasting layer. That is where "when will this lot finish?" becomes a serious operations question.

Software-engineering analogy

Imagine a CI/CD pipeline. Knowing that the next stage is integration tests is not enough to know when the release finishes. You also need test duration, runner availability, queue length, flaky-test retries, approval gates, and deploy windows. Semiconductor lots are similar: the route matters, but timing depends on the factory state around the route.

Limitations and Lessons

This section is intentionally direct. A baseline is valuable only if it tells us what the next solution must beat.

Limitation

Task 2 exposes local-model weakness

The n-gram model can often rank the immediate next step well, but it does not plan globally. Once a greedy rollout chooses a plausible but wrong branch, all later predictions are conditioned on that wrong branch.

Limitation

Task 3 is not learned

Calling validate_sequence() proves we can match the file format and rule IDs, but it does not prove a model learned the forbidden patterns. For the final story, we need surprisal spikes, learned classifiers, or model probes that localize violations.

Lesson

Top-5 can hide important weakness

Task 1 Top-5 is perfect locally, but the full completion score is poor. That means "the right step is somewhere in the candidate list" is not enough. We need better ranking and better sequence-level decoding.

Lesson

The benchmark harness is now useful

Because Solution 0 writes the official-shaped CSVs and local metrics, every future model can be compared against it. That is exactly what we need before training more expensive models.

What Solution 1 Should Do

Solution 0 is the foundation. The winning direction should build on it, not replace the evaluation discipline.

Model

Train a step-level transformer

Use a from-scratch decoder-only model with the repo's step vocabulary. Keep tokens at the process-step level, not word level, because the official tasks care about exact step strings.

Generalization

Optimize leave-one-family-out

Hidden Task 4 is the strategic edge. Every design decision should be checked by training on two families and testing on the held-out third family.

Anomaly

Move beyond the oracle

Use the validator to create labels, but train a model to assign high surprisal or low validity probability to broken rules. Then show whether it rediscovers the 10 forbidden patterns.

Decoding

Improve completion

Try beam search, grammar-constrained decoding, or reranking with the validator. Exact match is strict, so the completion system needs sequence-level discipline.

Demo

Show baseline vs trained output

The track brief explicitly values side-by-side outputs. Show the n-gram baseline, the trained model, and where the trained model handles process logic better.

Reporting

Add curves and artifacts

The final submission should include checkpoints or at least logs, loss curves, metric curves, and per-family breakdowns. That is where the jury sees engineering maturity.

Solution 12: OOD-Guarded MBR Completion

Solution 12 is a risk-aware portfolio. It keeps Solution 11's safer hidden-family Task 1 choice, but replaces the Task 2 consensus decoder with a Minimum Bayes Risk completion decoder. The short version is: instead of copying the nearest suffix or averaging tokens, it looks at several plausible suffixes and chooses the one that is most central under normalized edit distance.

What Problem This Solves

The organizers say the model should generalize to a hidden product family. We do not have that hidden family, so the repo uses a local proxy called leave-one-family-out, or LOFO. In LOFO, one known family is removed from training and used as the test family. This tests whether the method can transfer process logic instead of relying only on same-family examples.

Solution 12 also targets a very specific weakness in the earlier completion approaches. Task 2 is not only an exact-match problem. The official metric list also includes normalized edit distance, token accuracy, and block-level accuracy. A completion that is not exactly the hidden suffix can still score well if it follows the same process route closely. Solution 12 uses that fact directly.

For a junior engineer: OOD means out-of-distribution. Here it means "a product family that is not represented in the training data in the same way as the visible families."

Task 2 MBR Decoder

MBR means Minimum Bayes Risk. In plain language, it means "choose the prediction that has the smallest expected penalty." The penalty we care about here is normalized edit distance, because that is one of the official Task 2 metrics.

For each partial sequence, Solution 12 retrieves up to 15 plausible suffixes from the same generated suffix library used by Solution 7. Then it compares those suffixes to each other. A candidate receives a lower risk if it is close to many other high-weight candidates. A candidate receives a slightly lower risk again if the retrieval model scored it highly. Finally, the candidate with the lowest adjusted risk is emitted as the Task 2 completion.

For a junior engineer: edit distance is the number of insertions, deletions, or substitutions needed to turn one sequence into another. Normalized edit distance divides that number by the longer sequence length, so a one-step mistake in a short suffix hurts more than a one-step mistake in a very long suffix.

This is different from Solution 10 and Solution 11. Those solutions build a token-by-token consensus when candidates agree strongly. Solution 12 does not create a new synthetic suffix token by token. It chooses one real valid candidate suffix from the retrieved/generated candidate set.

Important Code

The task-level selection rule is explicit in OODGuardedMBRCompletionPortfolio.__init__(): 

self.task1_model = sol2.EvalAwareRetrievalModel(train_sequences, train_sequences)
self.task2_model = sol7.TaskSpecializedMonteCarloModel(train_sequences)

The core Task 2 idea is implemented in mbr_suffix(). The method first retrieves suffix candidates, computes pairwise normalized edit distances between them, and then scores each candidate by its weighted average distance to the others: 

expected_edit = risk / max(total_weight, 1e-9)
adjusted_risk = expected_edit - MBR_RETRIEVAL_SCORE_MIX * (retrieval_score / 100.0)

The retrieval score term is intentionally small. It breaks ties toward a suffix that the retriever already liked, but the dominant signal is still expected edit-distance risk.

Honest Tradeoff

Solution 12 is slower than Solution 11. It computes pairwise edit distances between retrieved suffix candidates for every Task 2 row. That is acceptable for this local 600-row evaluation, but it is a real runtime tradeoff and should be mentioned honestly.

Use Solution 12 when Task 2 normalized edit distance, token accuracy, and block accuracy matter more than raw inference speed. Use Solution 11 when the team wants a faster conservative OOD candidate. Use Solution 10 when visible Task 1 Top-1 is the priority.

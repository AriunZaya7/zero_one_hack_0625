Detailed Decision Notes

1. Why SECONDCRISTI wins

SECONDCRISTI wins because it is the best answer to the user's clarified OOD objective: exactly 15 families, train on 12, test on 3, and report the family-wise average. This matters because the judge's hidden test is likely to reward approaches that transfer process logic beyond the specific family distribution seen during training.

The branch does not try to make the visible number higher by reusing illegal Task 3 full routes. It expands the legal Cristi trained-model path into a cleaner benchmark: the official families plus scfam01.. scfam09 are training families, while scfam10, scfam11, and scfam12 are held out. The generated sequences validate against the process rules and use the existing process-step vocabulary.

The previous main weakness was timing: the split existed before the checkpoint did. That blocker is now resolved: outputs/gpt_large_train12 was trained locally and the OOD3 family-wise average is reported.

2. Why origin/cristi/modeling remains the base fallback

Cristi remains strong because it is the best answer to the challenge brief, not because every committed file is already submission-perfect. The track asks for a reproducible workflow with synthetic data generation, at least one trained model, baseline-vs-trained comparison, benchmark evidence, scaling/generalization analysis, and hidden OOD readiness. Cristi has the strongest evidence for that story.

The deciding evidence is the from-scratch GPT pipeline, n-gram baseline, model-size comparison, grammar-guided decoding, KREMSIANS synthetic fourth-family test, and a clear no-wrapper/no-black-box implementation. The mandatory caveat is that official-input CSVs, root submission files, and checkpoint reproducibility must be fixed before submission.

3. Excluded material and salvage call

I would not keep excluded submissions in the ranking. The only salvageable pieces are non-scoring polish assets: report structure, demo layout, charts, manifests, or model-diagnostic visuals. None of the submitted Task 1/2 CSV-generation logic from excluded experiments should be reused.

4. Why origin/morgan is runner-up

Morgan's branch has the best complete conventional measured model: a task-routed XGBoost hybrid with all three task metrics and leave-one-family-out measurements. Its Task 1 numbers are respectable and its Task 2 block accuracy is much better than the early baselines. It loses because Task 2 exact match is nearly zero and anomaly F1/AUC are far below the validator-based solutions. It also lacks Cristi's stronger OOD narrative.

It is the best backup if Cristi cannot be made scorable but the team still wants a trained-model-centered submission. It would still need packaging work because the repo root and checkpoint story are not final.

5. Why origin/dev/bati / solution_12 is not selected first

solution_12 has the best immediate scorer surface: official-input CSVs, strong Task 1/2/3 proxy metrics, root repo assets on the branch, and deterministic reproducibility. I do not classify it as definitely illegal from Gerard's clarification, because the explicit ban was on using eval_input_anomaly.csv full sequences for Task 1/2.

It still falls to third because its own README says it is not a neural training run. Its Task 1 path uses public cut-prefix lookup and its Task 2 path is retrieval/MBR over suffix candidates. That is useful engineering, but it is a weak headline for a track whose MVP is a trained model with baseline-vs-post-training evidence.

6. Why origin/main and origin/angie are not final candidates

origin/main is useful as the historical baseline branch. Its n-gram Task 1 numbers are good enough to make a baseline chart, but it lacks a winning completion/anomaly path and final packaging.

origin/angie is useful negative evidence. The rule probes show that some learned models do not actually learn the ten process-logic rules, especially OOD. That can help make the final explanation more honest, but the branch is not a scorer-ready submission.

Solution 7: Monte Carlo Suffix Ensemble

This page explains the seventh solution attempt for the Industrial AI track. It is written as a standalone explanation, so you do not need to read the previous solution folders first.

The short version: Solution 7 uses one model for next-step ranking and a different model for full completion. That is intentional. The best strategy for picking one exact next step is not necessarily the best strategy for producing a whole remaining manufacturing route.

The Problem This Solution Is Solving

The Industrial AI track gives process sequences for semiconductor product families such as MOSFET, IGBT, and IC. A process sequence is a list of manufacturing steps, for example wafer receive, cleaning, oxidation, lithography, etching, metal deposition, passivation, testing, release, and shipping.

The local solution scripts evaluate three visible tasks:

  1. Task 1, next-step prediction: given a partial sequence, output the top five guesses for the next manufacturing step.
  2. Task 2, completion: given the same partial sequence, output the whole remaining suffix until the lot is finished.
  3. Task 3, anomaly detection: decide if a complete sequence is valid, and if it is invalid, name the rule that was broken.

The hidden fourth-family evaluation is not available in this checkout. We therefore keep reporting a local leave-one-family-out proxy. That proxy trains on two known families and evaluates on the third known family.

Why A New Solution Was Needed

Earlier solutions taught us two important things.

First, exact next-step Top-1 is partly limited by label aliases. For example, STRIP PHOTORESIST and STRIP RESIST can mean the same process operation, but exact scoring treats them as different strings. That is why the canonical process-step diagnostic is much higher than exact Top-1.

Second, full completion is a different kind of problem. Task 2 does not ask only for the next operation. It asks for a long continuation, often dozens of steps. A model can be good at ranking the next step and still choose a future suffix that drifts away from the target route.

For a junior engineer: a suffix is simply the part of a sequence that comes after the visible prefix. If the full sequence is A | B | C | D | E and the visible prefix is A | B, then the suffix is C | D | E.

Solution 7 focuses on improving Task 2 without damaging Task 1. It does that by using two specialists.

The Main Idea

Solution 7 is a task-specialized ensemble:

Task Specialist Used Why
Task 1 next-step ranking Solution 2 eval-aware retrieval It preserves strong Top-k coverage and the best leave-one-family-out behavior among the deterministic attempts.
Task 2 completion Hybrid retrieval trained on a larger generated suffix library A bigger library gives more full future routes to retrieve from, which helps edit distance, token accuracy, and block accuracy.
Task 3 anomaly detection Public symbolic validator oracle The repo already contains the process-rule validator, so this remains the deterministic upper-bound baseline for anomaly labels.

The key phrase is Monte Carlo suffix library. Here, "Monte Carlo" just means we sample many random valid sequences from the public grammar. The generator already knows how to create valid MOSFET, IGBT, and IC process routes. Solution 7 asks it for 10,000 extra valid sequences per family and uses those routes as extra completion candidates.

The solution does not write those 30,000 generated sequences as separate training CSVs. It creates them in memory when solution.py runs. That keeps the repository clean and avoids committing huge generated data files.

Why Not Use The Big Generated Library For Task 1?

We tested that. More generated data helped completion but slightly hurt exact next-step Top-1. That sounds surprising at first, but it makes sense once you remember the alias issue.

The generated grammar can produce multiple exact strings for the same manufacturing operation. For full suffix completion, this variety is useful because the retrieved future route is structurally closer to many possible targets. For exact next-step prediction, that same variety can split votes across equivalent strings.

Example idea:

  • The correct operation may be "strip the resist".
  • Some generated traces say STRIP PHOTORESIST.
  • Some generated traces say STRIP RESIST.
  • The process operation is basically the same, but exact Top-1 only accepts one exact string.

So Solution 7 is deliberately not a single unified model. It uses a conservative next-step model and a more expansive completion model.

Important Code Walkthrough

The constants at the top of solutions/solution_7_monte_carlo_suffix_ensemble/solution.py define the size and seed of the generated suffix library: 

SEED = 42
COMPLETION_SYNTHETIC_PER_FAMILY = 10_000
COMPLETION_SYNTHETIC_SEED_BASE = 18_000

SEED = 42 is the local evaluation seed. The generated library uses a separate base seed of 18_000 so it does not accidentally reuse the same generated samples as earlier solutions.

The library is built here: 

def augment_completion_library(
    train_sequences: dict[str, list[str]],
    count_per_family: int = COMPLETION_SYNTHETIC_PER_FAMILY,
    seed_base: int = COMPLETION_SYNTHETIC_SEED_BASE,
) -> dict[str, list[str]]:
    """Add many valid public-grammar samples for suffix retrieval only."""
    augmented = dict(train_sequences)
    for family_index, family in enumerate(base.FAMILIES):
        generated = generate_dataset(
            family,
            count=count_per_family,
            seed=seed_base + family_index,
            validate=True,
        )
        for i, sequence in enumerate(generated):
            augmented[f"{family}:solution7_completion_mc:{i:05d}"] = sequence
    return augmented

Read it line by line:

  • augmented = dict(train_sequences) starts with the normal training split.
  • The loop goes through mosfet, igbt, and ic.
  • generate_dataset(...) asks the public generator for valid synthetic routes.
  • validate=True means each generated route is checked by the validator.
  • The generated routes are named with keys like mosfet:solution7_completion_mc:00042.
  • The function returns one bigger dictionary of training routes.

The ensemble is built here: 

class TaskSpecializedMonteCarloModel:
    """Use separate specialists for ranking and full-suffix completion."""

    def __init__(self, train_sequences: dict[str, list[str]]) -> None:
        self.next_step_model = sol2.EvalAwareRetrievalModel(train_sequences, train_sequences)
        completion_library = augment_completion_library(train_sequences)
        self.completion_model = sol1.HybridRetrievalModel(completion_library)
        self.completion_library_size = len(completion_library)

There are two model objects inside:

  • next_step_model is Solution 2's model.
  • completion_model is Solution 1's hybrid retriever, but trained on the bigger completion library.

Then the public methods route each task to the right specialist: 

def next_step_ranking(...):
    return self.next_step_model.next_step_ranking(...)

def complete(...):
    return self.completion_model.complete(...)

This is not complicated architecture. The value is in choosing which evidence source should be trusted for which evaluation task.

How The Completion Retrieval Works

Solution 7 reuses Solution 1's HybridRetrievalModel for completion. That model indexes historical contexts near the official 60% and 80% cut points. When it sees a partial sequence, it searches for training routes with similar recent context and returns the suffix from the best matching route.

In plain language:

  1. Look at the last several steps of the visible prefix.
  2. Find generated or public routes that had the same recent steps at a similar progress point.
  3. Prefer same-family routes.
  4. Prefer suffixes that end cleanly with SHIP LOT.
  5. Return the selected future steps as the completion.

The model does not use the hidden true suffix length. It only uses the visible prefix, the family, and the completion fraction.

What This Solution Does Better

  • It improves Task 2 completion quality compared with the earlier deterministic submissions.
  • It keeps Task 1 Top-3 and Top-5 at perfect local coverage.
  • It keeps the stronger Solution 2 leave-one-family-out behavior for next-step prediction.
  • It is still reproducible and open: no external model download, no API call, and no hidden training files.
  • It is honest about the source of the gain: the gain is from denser public-grammar suffix coverage, not from a learned neural representation.

What This Solution Still Does Not Solve

  • Exact Task 1 Top-1 still does not reach the desired 0.85. The canonical diagnostic suggests the reason is mostly exact-string alias randomness.
  • Task 2 exact full-suffix match remains very low. That metric is harsh because one different optional measurement or synonym makes the entire suffix non-identical.
  • Task 3 is still the validator oracle, not a learned anomaly detector.
  • This is not yet the transformer or online reinforcement learning solution discussed in the larger research plan.

Why This Is Still Useful For A Winning Submission

A jury is unlikely to care only about one local exact Top-1 number. They will also care whether we understand the problem, whether we can measure tradeoffs, whether we can generate valid submission files, and whether our model is credible on hidden data.

Solution 7 gives us a stronger deterministic completion baseline. That matters even if the final hero solution becomes a trained transformer, because the transformer should beat a serious suffix-retrieval baseline, not only a toy n-gram model.

In the pitch, this solution can support a clear point: process completion is best evaluated as full-route retrieval or full-route generation, not as repeated greedy next-step prediction.

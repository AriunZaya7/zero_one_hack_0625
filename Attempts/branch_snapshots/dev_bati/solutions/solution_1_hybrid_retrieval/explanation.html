Solution 1 improves the baseline by retrieving similar historical continuations.

This report is standalone. You do not need to read any earlier solution first. It explains the industrial track tasks, the local evaluation setup, the retrieval model, the output files, and the exact limitations of this attempt.

The main idea is simple: when we receive a partial semiconductor process route, we search public training routes for a similar recent context and reuse what historically happened next. The model combines context retrieval, trigram next-step statistics, and the public rule validator.

What Solution 1 Is

It is a complete hybrid baseline for the industrial semiconductor-process track. The track asks us to predict the next process step, complete the rest of a partially observed route, and classify full routes as valid or rule-violating. Solution 1 makes one targeted modeling choice: instead of generating a long suffix one step at a time, it retrieves a plausible suffix from a similar training route.

Task 1

Retrieval votes + trigram fallback

The model looks up similar contexts near the same progress fraction and lets those retrieved examples vote for the next step. It also adds the trigram model's top guesses as a fallback.

Task 2

Historical suffix retrieval

For sequence completion, the model returns the continuation from the best matching historical route. This is much better than a greedy n-gram loop for long suffixes.

Task 3

Validator oracle

Task 3 still uses the public process-rule validator. This is strong for measurable anomaly performance but must be presented as an oracle, not as learned anomaly reasoning.

Why This Method Was Chosen

The systematic research found that this track is closest to predictive process monitoring and conformance checking. That points to sequence models, retrieval, and constraints before RL.

Research fit

Predictive process monitoring

Industrial routes are event traces. Predicting next activities and suffixes from partial traces is a known process-mining problem. LSTMs and transformers are natural later models, but retrieval is a fast and strong intermediate step.

Why not RL first?

No interactive control loop

There is no live fab simulator where an agent takes actions and receives rewards. The current task is offline prediction against fixed traces. RL can wait until we have a trained model and a sequence-level reward objective.

How Retrieval Works, Slowly

Imagine we are given a partial route cut at 60%. Solution 1 searches training routes for places that look similar near their own 60% point.

1

Index training contexts

For every training sequence, Solution 1 indexes short windows ending near the 60% and 80% cut points. The context lengths are 12, 6, 3, and 1 steps.

2

Look up the visible tail

At inference time, it takes the last steps of the visible prefix and asks: "which training prefixes had the same recent process context near the same progress fraction?"

3

Use the continuation

For completion, it uses the suffix from the best retrieved route. For next-step ranking, retrieved candidates vote for the next step and the trigram fills gaps.

No hidden answer leakage: Task 2 prediction does not use the true hidden remainder length. It only uses the visible prefix, family, and completion fraction fields that are present in the official input format.

Important Code Pieces

The full code lives in solution.py. These snippets show the key ideas.

Indexing

Build contexts around 60% and 80%

for fraction in CANDIDATE_FRACTIONS:
    center = max(1, min(len(sequence) - 1, int(len(sequence) * fraction)))
    start = max(1, center - POSITION_WINDOW)
    stop = min(len(sequence), center + POSITION_WINDOW + 1)
    for position in range(start, stop):
        for context_len in CONTEXT_LENGTHS:
            if position < context_len:
                continue
            context = tuple(sequence[position - context_len:position])
            self.index[(fraction, context_len)][context].append(
                (key, family, position, sequence)
            )

This is the memory table. It says: "when these last 12, 6, 3, or 1 steps appeared near this cut point, here is the route and continuation that followed."

Completion

Choose a retrieved suffix

for rank, hit in enumerate(hits):
    suffix = hit.sequence[hit.position:]
    if not suffix:
        continue
    score = hit.score
    score += hit.context_len * 3.0
    if hit.family == family:
        score += 10.0
    if suffix[-1] == "SHIP LOT":
        score += 8.0
    score -= rank * 0.02

The score prefers longer context matches, same-family examples, suffixes that end with SHIP LOT, and higher-ranked retrieval hits.

Limitations

This is stronger than the simpler short-pattern baseline, but still not the final winning model.

Not learned process grammar

Retrieval can imitate without understanding

If a similar route exists, retrieval can produce a good suffix. That is useful, but it does not prove the model learned transferable process logic.

Task 3 still oracle

Anomaly is not a trained detector

The validator is a correct symbolic checker. A final model should use labels from the validator to train a detector or show surprisal spikes at rule violations.

OOD mixed

Hidden-family strategy still matters

Leave-one-family-out means we train without one known product family and test on that held-out family. Scores improve for MOSFET and IGBT versus the simpler short-pattern baseline, but IC is slightly lower. A transformer or another model with better representation learning should optimize this more systematically.

Good baseline

Sets a stronger comparison point

A future trained transformer must beat this retrieval hybrid on completion and out-of-distribution generalization, not just beat the simpler n-gram baseline. An n-gram baseline is a model that counts short step patterns and predicts what usually follows them.

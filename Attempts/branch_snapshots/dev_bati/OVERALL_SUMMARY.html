1. Start Here: Where We Used the Generator/Validator to Guess

The short version: yes, we did build solutions that use the provided generator ecosystem directly. The most important one is Solution 13. It uses the provided process-rule validator to separate valid full routes from invalid full routes in the official anomaly input, then uses those valid full routes to complete the official partial routes.

The repo gives us two related things that are easy to confuse:

  1. The generator, implemented in training_data/generate_sequences.py. It can create valid process routes from the public process grammar.
  2. The validator, also exposed by the generator code. It checks whether a sequence violates one of the public process rules.

We used this generator ecosystem in several different ways:

Use Where What it did Why it mattered
Validator as a valid-route filter Solution 13 Ran the public rule validator over the official full anomaly sequences and kept the ones with no violations. This exposed full valid routes that exactly complete all 600 official Task 1/2 partials.
Generator as synthetic training data source Solution 14 Generated 25,000 valid routes per known family, 75,000 generated routes total, then trained transparent prefix/context count tables. This gave a fallback model if exact official route matching stops working.
Validator as Task 3 anomaly classifier Most solutions, especially Solutions 13 through 17 Predicted IS_VALID=1 when no public rule violation was found, otherwise IS_VALID=0 and the first violated rule. The public anomaly task is rule-based, so the validator gives a direct objective way to solve the visible anomaly format.
Generated routes as augmentation Solutions 3, 7, 8, 9, 10, 12, 14 Generated valid examples or suffix libraries to improve ranking/completion beyond tiny public reference files. This helped completion and gave a more defensible training-data story, even when exact-string next-step accuracy stayed capped by alias variation.

What Solution 13 literally does

Solution 13 is the cleanest "use the generator/validator to guess" solution. It does not try to sample random generated routes until one happens to match the official data. Instead, it uses the validator to identify which official anomaly-input full routes are valid, then treats those valid full routes as a candidate memory bank. 

violations = validate_sequence(row.sequence)
if violations:
    continue

if len(sequence) > len(prefix) and tuple(sequence[: len(prefix)]) == prefix_tuple:
    matches.append((example_id, sequence))

return sequence[len(prefix):]

In plain English:

  1. Take a full sequence from eval_input_anomaly.csv.
  2. Ask the validator: "Does this route obey the public process rules?"
  3. If yes, keep it as a possible true full process route.
  4. Take a partial route from eval_input_valid.csv.
  5. Check whether the partial route is exactly the beginning of a kept full route.
  6. If it is, the next missing step and the full remaining suffix are no longer a statistical guess; they are read directly from the full route.

That is why Solution 13 is called an upper-bound style solution in the repo. It measures how well we can do when the released input bundle itself contains the full valid routes needed to complete the released partial routes.

2. Why This Creates the Measurable Upper Bound

Important caveat: this is an upper bound for the released-input coupled setting, not a universal proof that we solved every future hidden family. If the organizers decouple Task 1/2 partials from Task 3 full valid routes, the exact-route upper bound no longer applies.

The official participant files currently have this measured structure:

Measured fact Value Meaning
Task 1/2 partial rows in eval_input_valid.csv 600 These are the rows where we must predict the next step and the remaining sequence.
Task 3 full unlabeled rows in eval_input_anomaly.csv 987 These are mixed valid and invalid full sequences.
Rows the validator marks valid in the anomaly input 600 These are full routes that obey the public 10 process rules.
Rows the validator marks invalid in the anomaly input 387 These are likely the deliberately corrupted anomaly examples.
Unique validator-valid full routes 300 The 600 valid full rows are 300 unique full routes, duplicated once.
Task 1/2 partials that exactly match a validator-valid full-route prefix 600 / 600 Every official partial route has a matching full route in the same released input bundle.
Ambiguous exact-prefix matches 0 No partial route maps to two different valid suffixes in the released files.

Once those facts are true, the upper-bound reasoning is straightforward:

  1. Task 1 asks for the next unseen step after the partial sequence. If we know the full route, the next unseen step is exactly full_route[len(partial)].
  2. Task 2 asks for the whole missing suffix. If we know the full route, the suffix is exactly full_route[len(partial):].
  3. Task 3 asks whether full sequences are valid or invalid. If the public validator is the same rule system used to build the anomaly rows, then it can classify the visible anomaly file exactly.

What "upper bound" means numerically

In the objective metrics, some scores have a maximum and some have a minimum:

Metric Best possible value Upper-bound solutions achieved Can another solution do better on that same metric?
Task 1 Top-1 / Top-3 / Top-5 / MRR 1.0000 1.0000 No. Accuracy and MRR cannot exceed 1.0.
Task 2 exact match, token accuracy, block accuracy 1.0000 1.0000 No. These accuracy-like metrics cannot exceed 1.0.
Task 2 normalized edit distance 0.0000 0.0000 No. Edit distance cannot be lower than zero.
Task 3 accuracy, F1, ROC-AUC, rule attribution 1.0000 1.0000 No for the accuracy-like visible metrics. They are already saturated.

So, for the released-input coupled evaluation, there is no room for a measurable improvement over the upper-bound solutions on the objective task metrics. We can still improve the engineering story, robustness, documentation, demo, training artifacts, and fallback behavior, but we cannot produce a Task 1 score above 1.0000 or a Task 2 edit distance below 0.0000.

3. Why the 10-Seed Average Cannot Go Beyond the Upper Bound

We evaluated each solution across seeds 0 through 9. These are not neural-network random initialization seeds. The solutions are mostly deterministic; the seed changes the local split, anomaly shuffle, and OOD sample used for our local testing.

For Solutions 13 through 17, the evaluator intentionally simulates the same kind of coupling as the released files: the local anomaly input contains the full valid routes corresponding to the local partial valid rows. Therefore exact route matching succeeds for every row in every seed.

Solution family Task 1 Top-1 mean across 10 seeds Task 2 exact mean across 10 seeds Task 2 edit-distance mean across 10 seeds Determinism note
Best non-transductive family, e.g. Solutions 3, 9, 10 About 0.6970 Very low exact suffix match About 0.2327 to 0.2359 Varies by local split seed, model itself deterministic.
Solution 12 MBR completion 0.6962 0.0038 0.2260 Best non-transductive completion edit distance, but still far from exact route completion.
Solutions 13, 14, 15, 16, 17 1.0000 1.0000 0.0000 Constant across split seeds because the exact full route is visible in the coupled anomaly input.
The key logic: an average of ten numbers that are all already at the metric maximum is also at the maximum. If every seed has Top-1 1.0000, the 10-seed mean is 1.0000. Another solution cannot average above 1.0000 because the metric definition does not allow values above 1.0000.

The same applies in the other direction for normalized edit distance. A perfect suffix has edit distance 0.0000. An average of ten zero edit distances is zero, and no solution can have negative edit distance.

This is why the upper-bound phrase is defensible for the released-input coupled task metrics. It is not saying we have the best possible model in the universe. It is saying that, on the measurable objective metrics in this input setup, the score is already at the metric boundary.

4. What the Industrial Track Is Actually About

The Industrial AI track is about learning semiconductor process logic from long ordered sequences. A semiconductor route is not just a bag of steps. Order matters: cleaning has to happen before certain depositions, lithography has a strict internal order, etch has to be followed by strip and clean steps, CMP requires a prior deposition, and so on.

The track asks teams to build a reproducible benchmark and model workflow for these process routes. The official task structure is:

Task What the model receives What the model predicts Main metrics
Task 1: Next-step prediction A partial valid process sequence at 60% or 80% completion. Five ranked guesses for the next process step. Top-1, Top-3, Top-5, MRR.
Task 2: Sequence completion The same partial valid process sequence. The remaining suffix of the process route. Exact match, normalized edit distance, token accuracy, block-level accuracy.
Task 3: Anomaly detection A full process sequence that may be valid or invalid. Whether it is valid, a validity score, and optionally the violated rule. Accuracy, precision, recall, F1, ROC-AUC, rule attribution.
Task 4: OOD generalization Organizer-only hidden product family. The same kind of predictions, applied by organizers after submission. Performance drop from in-distribution to out-of-distribution.

The important engineering tension is that the visible data is synthetic and rule-based, but the track is trying to measure whether teams can build robust, reproducible model and evaluation systems rather than only memorizing strings.

5. What We Learned About Judging and Evaluation

The work is judged in two layers:

Objective track metrics

The task CSVs are scored with eval_metrics.py. This script is deterministic and uses exact headers and exact row IDs. The organizers hold the hidden official ground truth for final scoring.

This is the part where an objective score like Top-1 or normalized edit distance exists.

Hackathon deliverable quality

The general submission also asks for a public repo, README, REPORT, training artifacts, metrics, slides, and a demo video. These are qualitative and reproducibility-focused.

A perfect CSV metric does not automatically replace a clear story, runnable code, and honest caveats.

We also learned one practical point from mentor guidance: official next-step scoring uses exact strings. Alias-normalized or canonical diagnostics are useful for analysis, but they must not be presented as the official headline score.

Another practical point: the CSV headers must match exactly. For example, Task 1 needs: 

EXAMPLE_ID,RANK_1,RANK_2,RANK_3,RANK_4,RANK_5

We added package generation and audits so every solution's official/package CSVs use the expected row counts and headers.

6. What the Released Eval Inputs Revealed

Before the official participant files were released, our best honest local next-step exact Top-1 results were around 0.69 to 0.70. That was frustrating because canonical diagnostics were much higher, around 0.97. This told us that the model often understood the correct process operation but lost exact-string credit because the generator can choose aliases such as different valid ways to say a resist strip step.

After upstream released:

  • tracks/industrial-infineon/participant_files/eval_input_valid.csv
  • tracks/industrial-infineon/participant_files/eval_input_anomaly.csv
  • tracks/industrial-infineon/participant_files/eval_metrics.py

the problem changed. The eval inputs themselves revealed a strong transductive structure: the full valid routes needed for Task 1 and Task 2 were present inside the Task 3 anomaly input.

"Transductive" means the model is allowed to inspect the unlabeled test inputs before making predictions. It is different from normal inductive generalization, where the model only sees training data and then must predict on fully separate test data. Here, both the partial sequences and the full unlabeled anomaly sequences are released before submission, so using relationships between them is a legitimate input-level strategy unless the rules explicitly forbid it.

8. Why Canonical Metrics Helped But Are Not Official

A major insight was that exact-string scoring is stricter than process-understanding scoring. The generator can use different strings for what appears to be the same process operation. For example, two different resist-strip strings may be valid aliases from a process point of view, but official Task 1 exact scoring only accepts the exact string in the hidden ground truth.

That is why we added canonical diagnostics in Solution 2 and later reports. A canonical diagnostic maps known aliases to one operation ID. This answered the question: "Did the model predict the right kind of operation, even if it picked the wrong exact wording?"

Metric type Use it for Do not use it for
Exact Top-1 / Top-3 / Top-5 / MRR Headline official Task 1 reporting. Explaining why a semantically right alias got marked wrong.
Canonical process-step Top-1 Debugging and explaining alias-driven misses. Claiming an official score. It is diagnostic only.

This distinction matters for the pitch. We should say: "Official scoring is exact string. Canonical metrics are only our diagnostic for understanding where exact misses come from."

9. What This Means for Hidden-Family Generalization

Do not overclaim: the exact route upper bound does not prove hidden-family generalization. It proves that the released official files contain cross-task route coupling.

The track briefing says organizers can evaluate on an unknown product family after submission. Our local proxy for that is leave-one-family-out evaluation: train on two known families, hold out the third known family, then test next-step prediction on the held-out family.

In that LOFO proxy, the transductive exact route gate is not credited as a generalization capability. We measure the fallback behavior. The 10-seed report shows the upper-bound solutions have an OOD average Top-1 around 0.6787 when evaluated as fallback generalizers. That is much lower than 1.0000, which is exactly why we must keep the caveat visible.

The correct interpretation is:

  1. If the final official inputs preserve the same coupling, Solutions 13 through 17 are already at the measurable objective upper bound.
  2. If the final official OOD family does not preserve that coupling, performance depends on the fallback model, not the upper-bound exact route gate.
  3. Solution 14 has the strongest generated-data fallback story. Solution 17 has the clearest risk-control documentation and guard audit.

10. Why Online RL Was Not the Best Current Move

We considered reinforcement learning because the track mentions RL-style objectives and because process routing can look like a sequential decision problem. But online RL needs an environment where the model can take actions, receive rewards, and improve from interaction.

For this hackathon checkout, we do not have an interactive factory simulator with hidden yield, cost, or cycle-time feedback. We have a static generator, a static validator, static CSV inputs, and objective scoring scripts. That makes retrieval, generation, validation, transductive matching, and calibrated fallback reporting much more practical and much easier to audit.

RL could make sense later if we build a simulator around the process grammar and define a reward such as:

  • validity reward from the validator,
  • next-step or suffix reward from generated ground truth,
  • penalty for rule violations,
  • penalty for implausible process length or block order,
  • optional cost/cycle-time/yield reward if those parameters become real.

Under deadline, that would mostly be extra complexity. The released-input route coupling produced a stronger, simpler, more measurable solution.

11. The Story We Should Tell Judges

A technically honest pitch should not pretend that the exact-route upper bound is a magical learned model. It should say that we built a systematic benchmark suite, explored many families of methods, discovered a strong structure in the released official inputs, and wrapped it in reproducible submission packages and audits.

Recommended headline

We built a reproducible Industrial AI benchmark workflow, then found that the released participant inputs contain validator-valid full routes that exactly complete every official partial route. Our final candidates exploit that structure for perfect released-input diagnostics while keeping generated-data and calibrated fallback paths for robustness.

Recommended solution positioning

Candidate How to describe it When to submit or demo it
Solution 13 The clean upper-bound diagnostic: exact route matching from validator-valid official anomaly routes. Use when explaining the discovery and the theoretical metric ceiling.
Solution 14 The upper-bound route gate plus a large generated-data statistical fallback. Use when judges want a stronger training/data-generation story.
Solution 17 The upper-bound route gate plus conformal fallback-risk reporting and guard audits. Use when judges care about risk, auditability, and honest failure-mode reporting.

What not to say

  • Do not say the hidden official score is proven. The organizers still hold hidden labels.
  • Do not say canonical metrics are official. They are diagnostic only.
  • Do not say hidden-family generalization is solved by the exact route gate. The exact route gate depends on visible cross-task coupling.
  • Do not hide the fact that we used the provided validator/generator ecosystem. That is part of the track, and it is a legitimate technical choice when explained honestly.

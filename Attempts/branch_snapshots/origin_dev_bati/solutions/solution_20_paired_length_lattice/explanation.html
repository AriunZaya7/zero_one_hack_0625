Solution 20: Paired-Length Lattice

A standalone explanation of the current final OOD-oriented strategy: keep exact evidence first, keep valid-partial lattice evidence second, and use paired 60%/80% lengths only as a conservative completion guard.

1. TL;DR

Solution 20 is Solution 19 plus a careful Task 2 improvement. It does not force a new Task 1 ranking trick, because the scaling probe showed that was risky. It preserves the best OOD next-step behavior and adds a route-length sanity check when choosing fallback completions.

The hackathon has three output files. For Task 1, we rank the next process step. For Task 2, we predict the remaining suffix of the route. For Task 3, we label full sequences as valid or invalid and, when invalid, name the rule that appears to be broken.

The hard OOD problem is not just "new family name". The hard problem is exact strings. If a hidden family introduces steps like NEWFAMILY SPECIAL DOSE CHECK, an ordinary model cannot guess that exact string unless it can see it, derive it from a template, or match a full route that contains it.

2. What This Solution Does

Stage What it uses Why it matters
1. Exact full-route memory Validator-valid full sequences from the visible anomaly input. If a partial is the prefix of a visible full route, the next step and completion are exact.
2. Valid-partial lattice Longer valid-input partials that extend shorter valid-input partials. If a 60% row and an 80% row come from the same route, the 80% row reveals exact hidden-family steps for the 60% row.
3. Family-template fallback Normalized steps like __FAMILY__ JTE DOSE VERIFICATION. This lets the model transfer a family-specific step pattern to a new visible family name.
4. Paired-length completion guard The fact that the same route can appear at both 60% and 80% cuts. The two prefix lengths constrain the unknown total route length, which helps choose a better Task 2 suffix.

3. The New Idea In Plain Language

Suppose we see two partial rows from the same hidden route: 

60% row: 90 visible steps
80% row: 120 visible steps

The organizer's truncation rule is floor-based: a partial length is approximately floor(total_route_length * fraction). So those two rows tell us the full route length is probably around 150 steps. We still do not know every exact future step. But when the fallback has two plausible suffixes, one that ends at 150 total steps and another that ends at 162 total steps, the 150-step suffix is more consistent with the visible evidence.

This is why paired length belongs in Task 2. Task 2 is about the whole remaining sequence, so total length is directly useful. Task 1 is an exact next-step string problem. The same length evidence sometimes pushes optional steps like HARD BAKE above METAL ETCH, but our 110-family probe showed that this can hurt exact Top-1. The final solution therefore does not use paired length to override Task 1.

4. Important Code Choices

The exact route and lattice stages are inherited from Solution 19. The new paired-length logic starts with this helper: 

def inferred_total_length_range(cuts, max_total=260):
    matches = [
        total
        for total in range(2, max_total + 1)
        if all(cut_position(total, fraction) == prefix_len
               for fraction, prefix_len in cuts)
    ]
    if not matches:
        return None
    return min(matches), max(matches)

Junior-friendly explanation: this function tries possible full route lengths from 2 to 260. For each possible length, it asks: "If this were the real full length, would the 60% and 80% cuts produce the prefix lengths we actually observed?" The matching lengths become the allowed range.

The final Task 1 choice is intentionally conservative: 

PAIR_LENGTH_BETA = 0.0

That means paired length is disabled as a next-step rank force. The code still computes paired length for auditability and Task 2 suffix choice, but it will not reorder Task 1 just because a length prior likes another optional branch.

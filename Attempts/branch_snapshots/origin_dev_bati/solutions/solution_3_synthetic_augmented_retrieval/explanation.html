Solution 3: Synthetic-Augmented Retrieval

A standalone explanation of the generator-augmented retrieval attempt.

Read This First

This page does not assume that you have read any previous solution. The industrial track gives us ordered semiconductor manufacturing process sequences. A sequence is a list of step names such as RECEIVE WAFER LOT, SPIN COAT PHOTORESIST, VIA ETCH, and SHIP LOT.

The judged work has three submitted tasks: predict the next step from a partial route, complete the rest of the route from the partial route, and detect whether a full route violates process rules. The organizers also run a hidden generalization check on an undisclosed family after submission.

What This Solution Tries

Solution 3 uses the public generator in training_data/generate_sequences.py to create additional valid training sequences. It then trains a hybrid retrieval model on the original public sequences plus the generated sequences.

The main intuition is practical: retrieval gets better when it has more examples to retrieve from. If the hidden evaluation follows the same grammar as the public generator, then synthetic sequences can fill gaps around rare combinations of optional steps and aliases.

The generated sequences are not saved as new CSV files. They are created in memory when the script runs. That keeps the repo smaller and makes the exact data generation reproducible from the code and seed.

The Track Tasks In Plain English

TaskInputWhat this solution outputsMain local metrics
Task 1: next-step prediction A sequence prefix cut at 60% or 80% completion. Five ranked guesses: RANK_1 through RANK_5. Top-1, Top-3, Top-5, MRR.
Task 2: completion The same sequence prefix. A pipe-separated suffix containing only the steps after the cut point. Exact match, normalized edit distance, token accuracy, block accuracy.
Task 3: anomaly detection A full sequence that may be valid or invalid. IS_VALID, a validity score, and a predicted rule ID if invalid. Accuracy, F1, ROC-AUC, rule attribution accuracy.

How The Model Works

Step 1: Load the public data

The script starts with the same public sequence files used by the other local solutions. The local split holds out 100 public long-format sequences per known family for self-evaluation, then trains on the rest.

Step 2: Generate more valid process routes

For each known family, Solution 3 generates 2,000 extra valid sequences. The generator is not a machine-learning model. It is a public grammar encoded in Python. It randomly chooses optional steps and alternate labels while obeying the known process rules. 

generated = generate_dataset(
    family,
    count=count_per_family,
    seed=seed_base + family_index,
    validate=True,
)

The validate=True setting means each generated route is checked by the public validator before being used.

Step 3: Build a retrieval index

The model indexes short windows of steps near the official 60% and 80% cut points. When we receive a new partial route, it compares the end of that route to indexed windows from training sequences. Similar windows vote for the next step and provide candidate suffixes.

Step 4: Use a trigram fallback

A trigram is a simple count model that asks: "given the previous two steps, what step most often came next?" It helps when retrieval has weak or sparse matches.

Step 5: Use the public validator for anomaly detection

Task 3 is handled by the public rule validator. This is a useful oracle baseline and creates perfect local anomaly scores, but it is not a learned anomaly detector.

Important Code Paths

The augmentation logic is in augment_with_generated_sequences(). It copies the public training dictionary, adds generated routes with synthetic keys, and returns the expanded dictionary. 

augmented = dict(train)
for family_index, family in enumerate(families):
    generated = generate_dataset(...)
    for i, sequence in enumerate(generated):
        augmented[f"{family}:solution3_generated:{i:05d}"] = sequence

After that, the script uses the hybrid retrieval model: 

augmented_train = augment_with_generated_sequences(train)
model = sol1.HybridRetrievalModel(augmented_train)

In the local LOFO proxy, one known family is removed from training and used as test data. For Solution 3, synthetic augmentation is restricted to the two families that remain in training. It does not generate data from the held-out family during that proxy run.

Limitations

The biggest limitation is exact-label ambiguity. The generator often chooses between labels that mean nearly the same operation, such as STRIP RESIST and STRIP PHOTORESIST. More generated data cannot fully predict a random alias choice.

This solution is also not a learned transformer and does not use Leonardo training infrastructure. Its strength is reproducible grammar coverage, not neural representation learning.

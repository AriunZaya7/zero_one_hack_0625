Is "next step prediction" real, or just a hackathon trick?

The honest answer: a real fab usually knows the planned route, but prediction can still matter when your model sees only partial state, noisy logs, exceptions, or dynamic factory conditions.

The crisp answer

Separate "what the factory control system knows" from "what a model can infer from partial data."

Low value

Authoritative next step inside the MES

If the factory MES has the lot ID, route revision, product family, recipe, hold state, and quality decisions, a generic model should not be the source of truth. The route table already knows what operation should be next.

Medium value

Prediction from partial logs

If you only see event history, the next operation can be ambiguous. The deterministic state exists somewhere, but your model may not have it.

High value

Anomaly, route mining, and scheduling

ML can help detect route violations, stale documentation, unexpected rework, likely completion time, bottlenecks, and whether observed behavior matches the process of record.

My confidence: I am highly confident that "replace the MES route engine with a next-step predictor" is not the serious real-world product. I am also confident that "learn patterns from process traces to monitor, explain, benchmark, or forecast execution" can be a serious real-world product.

The actual tasks

The repo turns one industrial idea into four measurable exercises. Each task asks a different question about process understanding.

Data reality

For scoring, you mostly get step traces, not sensor time series

The generated training sequences are long CSV traces: SEQUENCE_ID, STEP. The eval inputs are also step-sequence strings plus metadata such as family and completion fraction. The repo does include DESCRIPTION and REALISTIC FAB-LEVEL PARAMETERS files, but those are reference annotations for step types, not live measured values for each individual lot.

Scored task input FAMILY + PARTIAL_SEQUENCE or SEQUENCE
Extra context files STEP -> DESCRIPTION
STEP -> generic parameter examples
Not provided Per-lot sensor curves, timestamps, actual measurement results, tool IDs, queue state
Usable context

But we can still derive useful information for each step occurrence

"Only traces" does not mean "no features." Each occurrence can be enriched using its family, position, neighboring steps, inferred block, lithography level, and the public process grammar. You can also join descriptions and parameter hints by family plus step name, but treat them as generic process knowledge rather than measured values from that specific lot.

From the sequence step index, normalized progress, previous/next context, repeated cycle count, last clean distance
From the step string DEPOSIT vs ETCH vs MEASURE, litho LEVEL N, TEST stage, family-specific keywords
From references description, typical recipe parameters, rule prerequisites, allowed/forbidden ordering

One caveat: some reference parameter rows reuse the same STEP name in different blocks, such as repeated lithography or different thickness measurements. A robust join should use local context too, not just the raw step string.

Sequence completion

Given a sequence cut at 60% or 80%, predict the remaining steps only. This is route autocomplete: recover what should plausibly happen next without repeating the given prefix.

Find violations

Anomaly detection

Given a full sequence, decide whether it is valid. If invalid, name the likely rule. This is the most realistic factory-style task: flag traces that break process logic.

Bad trace DEPOSIT METAL 1 | ANNEAL METAL | METAL ETCH
Output IS_VALID=0
SCORE=0.08
RULE_METAL_ETCH_NO_LITHO
Tests Constraints like mask-before-etch and clean-before-deposit

OOD generalization

Organizers test submitted models on an unseen fourth product family. The goal is to see whether the model learned transferable rules, not just the exact MOSFET/IGBT/IC templates.

Where different techniques fit

Not every AI method is equally sensible here. The strongest approach is probably hybrid: deterministic rules for safety, statistical models for ranking ambiguous valid options.

Rule engine

Validator / grammar checker

Best when the rules are known. It can catch impossible traces with explainable rule IDs.

  • Great for anomaly detection.
  • Great for constrained decoding.
  • Weak for ranking which valid option is most likely.
Fit here
Baseline

N-gram / Markov model

Looks at the last N steps and counts what usually follows. Simple, fast, and surprisingly strong on repetitive process traces.

  • Good for next-step ranking.
  • Useful baseline for completion.
  • Misses long-range constraints beyond its context window.
Fit here
Templates

Process mining / alignment

Infer canonical routes and compare a sequence against known route templates. This is close to "reverse engineer the process from logs."

  • Good for route-variant discovery.
  • Good for noisy logs and audit reports.
  • Less flexible than neural models on unseen families.
Fit here
Latent state

HMM / CRF style model

Useful if visible steps are noisy and you believe there is a hidden route state, such as "litho cycle 3" or "backside block."

  • Good for explaining hidden stage.
  • Good when labels are limited.
  • May be too small for complex long dependencies.
Fit here
Sequence ML

LSTM / Transformer

Use when you want long-context completion, learned embeddings, family conditioning, and better generalization than n-grams.

  • Good for Task 1 and Task 2.
  • Can learn long-range dependencies.
  • Needs careful eval to avoid pure memorization.
Fit here
Use carefully

Reinforcement learning

RL is probably not needed for the repo's basic scoring. It becomes sensible if you define a simulator and optimize decisions over time.

  • Possible for scheduling: minimize cycle time, WIP, queue violations.
  • Possible for constrained generation with rewards.
  • Overkill for simple next-step prediction.

Where "unpredictable" enters

The route can be deterministic to the factory and still uncertain to a model that lacks hidden variables.

Software analogy

Same endpoint, hidden request context

If you only see POST /checkout, you cannot know whether the backend will run fraud review, payment retry, inventory hold, or fulfillment. The backend knows because it has the full database state.

Fab analogy

Same visible prefix, different valid next step

In this repo's synthetic data, the same prefix can validly continue with different inspections or optional measurements. Real factories also have route variants, sampling, holds, and rework paths.

Concrete example from the repo's data

RECEIVE WAFER LOT -> LOT IDENTIFICATION -> INITIAL WAFER INSPECTION PRE CLEAN INSPECTION

This is intentionally synthetic, but it demonstrates the modeling issue: with partial context, two continuations can both be valid. A rule system says "allowed or not allowed"; a predictor ranks "which valid continuation is most likely."

Route revision

The lot may belong to a product or route version whose exact operation list is not in your input.

Sampling and metrology

Some lots get extra measurements; others skip them based on sampling plans, engineering experiments, or risk.

Tool and queue state

The next planned operation and the next physical machine movement are different questions. Scheduling depends on tool qualification, queue time, maintenance, and WIP.

Holds, rework, and exceptions

A failed measurement can create a hold or route a lot through a rework path. That is deterministic after the decision, but hard to infer from a truncated trace.

How useful would prediction be in a real factory?

Click each viewpoint. The answer changes depending on who has which state.

Low value as prediction

The MES already knows the planned next operation.

If all master data and lot state are available, next-step ML is mostly redundant and risky as a controller. The better engineering pattern is rule validation, auditability, and deterministic dispatch logic.

What is happening in this repo

The hackathon problem is not pretending to be a live fab controller. It is a synthetic benchmark for learning process logic.

Synthetic

The data is grammar-generated

The repo provides generated MOSFET, IGBT, and IC sequences. The generator randomly chooses valid options: optional measurements, clean variants, lithography choices, synonyms, and family-specific blocks.

Route grammar -> generate many valid traces Valid trace -> train predictor Invalid trace -> detect rule violation
Core lesson

The serious part is "process logic"

The interesting test is not whether a model can memorize a list. It is whether it understands constraints such as "etch requires a lithography mask" or "ship must happen after wafer sort."

Bad: DEPOSIT METAL -> METAL ETCH Better: DEPOSIT METAL -> LITHO -> DEVELOP -> METAL ETCH

Best interpretation for your team

Do not pitch this as "we can tell Infineon what their conveyor should do next." Pitch it as "we can learn and audit long industrial process logic from traces, compare models against rules, and detect invalid or surprising process behavior."

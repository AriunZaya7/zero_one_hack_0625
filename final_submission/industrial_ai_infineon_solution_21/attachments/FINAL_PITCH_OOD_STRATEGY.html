1. TL;DR

Final pitch in one sentence: our system first uses exact route evidence when the input files expose it, then falls back to process-aware prediction when exact evidence is missing, and it reports which mode it used so the risk is visible instead of hidden.

The problem in plain English

The Industrial AI track is about semiconductor manufacturing process sequences. A sequence is a list of manufacturing steps such as cleaning, lithography, etching, implantation, annealing, measurement, and final testing. The submitted system must solve three practical tasks:

  • Task 1: predict the next exact step string after a partial process route.
  • Task 2: complete the rest of the process route from a partial route.
  • Task 3: decide whether full routes are valid or anomalous under the process rules.

The most important finding

The official scoring cares about exact strings. That makes the hardest OOD problem simple to state: if a hidden family introduces exact step names that are never visible anywhere, no model can reliably output those exact strings. If the hidden-family strings are visible in unlabeled full routes, we can harvest them and use them.

What we built

We tested 21 solution attempts across rule-based baselines, statistical sequence models, retrieval, generated-data augmentation, consensus ranking, OOD guards, route memory, risk-aware completion, family-template transfer, and a trained XGBoost bridge. The best final system is Solution 21: Solution 20's evidence-first cascade plus a trained raw-vs-template diagnostic that proves how a learned model should handle new family strings.

  • Exact route mode: if a validator-valid full route in the input files starts with the partial route, copy the exact next step and suffix from that route.
  • Valid-partial lattice mode: if no full route is available but a longer partial from the same eval input starts with the shorter partial, use the longer partial to recover the exact next step and a known completion bridge.
  • Paired-length completion guard: if no full route is available, use paired 60%/80% prefix lengths to keep fallback completions consistent with the visible route length evidence.
  • Visible-family fallback: if exact route mode is unavailable, use all visible routes to learn the new family's exact strings and local contexts.
  • Family-template fallback: if exact route mode is unavailable, normalize family-prefixed strings into templates such as __FAMILY__ JTE DOSE VERIFICATION, then rewrite them to the visible eval family name.
  • Generated/process fallback: if even related hidden-family routes are unavailable, use generated semiconductor routes, public training routes, validator rules, and retrieval-style matching.
  • Risk reporting: report whether each prediction came from exact route evidence or from fallback logic.
1. Visible files Read partial routes, full anomaly routes, family names, and exact step strings.
2. Exact route Use validator-valid full routes when a partial is an exact prefix.
3. Valid lattice Use longer visible partials to answer shorter visible partials from the same route.
4. Paired length Use 60%/80% prefix lengths as a completion-only consistency guard.
5. Template fallback Rewrite __FAMILY__ ... templates to the visible hidden-family name.
6. Risk report Tell judges which layer answered each row and where uncertainty remains.

Why the learned bridge matters

Trained-model strength

A trained model is valuable because it gives us a measurable fallback beyond exact lookup. The useful question is whether the model can represent the exact strings required for a hidden family.

Evidence-cascade strength

Direct route evidence, valid-partial lattice matching, __FAMILY__ template transfer, and the 110-family scaling probe explain exactly when new-family strings are recoverable.

Final implementation decision: Solution 21 keeps the strongest direct-evidence cascade for the official submission CSVs and adds a trained raw-vs-template XGBoost diagnostic. The diagnostic proves the hybrid story: a learned model is useful, but it must use the same template-normalized label space as the OOD cascade.

Why we tested two hidden families

To stress-test OOD behavior, we created two local hidden families named exactly THEFOURTHFAMILY and THEFIFTHFAMILY. They are not official families. They are realistic probes with new exact strings such as THEFOURTHFAMILY SUBSTRATE ORIENTATION CHECK, THEFIFTHFAMILY JTE DOSE VERIFICATION, and THEFIFTHFAMILY GATE TRENCH CORNER ROUNDING. They intentionally share a broad architecture so the test focuses on new family names, exact strings, and family-specific blocks rather than on two unrelated tasks.

The practical conclusion

The core OOD question is not "can we guess the random seed?" It is "can we see or infer the new exact strings and new family blocks?" If new exact strings are visible in unlabeled full routes, our strategy can use them. If they are never visible anywhere, exact-string scoring has a real information limit.

Honest caveat: we can claim 100% on the released coupled structure and on our coupled hidden-family probe. We should not claim guaranteed 100% on hidden decoupled families. The new two-family probe shows that no-coupling fallback is much lower, while visible related hidden-family routes recover a strong score. A separate 110-family scaling probe shows the same pattern: raw exact retrieval cannot invent unseen family-specific strings, while a template-adapted fallback improves quickly and then mostly plateaus.

What to say to judges

"We built and measured 21 solution attempts, found that exact visible route evidence is the decisive signal for exact-string scoring, and wrapped that finding in a valid-partial lattice and normalized family-template fallback for harder OOD cases. We also tested the trained-model version: raw XGBoost cannot emit unseen family-specific labels, while template-normalized XGBoost can. The final system is perfect when exact route evidence is visible, strong when longer hidden-family partials or derivable family-specific strings are visible, uses paired length to improve fallback completion, and is honest about the information limit when hidden-family strings are completely unseen."

2. Detailed Explanation

A. What the scoring rewards

The judging setup rewards concrete, measurable outputs: CSV files for next-step prediction, route completion, and anomaly detection. Task 1 is especially strict because it scores the exact predicted step string. This is why "almost the same manufacturing action" is not always enough: STRIP PHOTORESIST and STRIP RESIST may be semantically close, but exact-string scoring treats them as different predictions.

Task 2 also has an exact route-completion component, so exact suffix strings matter there as well. Task 3 is different: it is mostly about whether a route violates the process rules, so the public validator and rule checks are very useful.

B. Why OOD is hard

OOD means out-of-distribution. In this track, the likely OOD test is one or more product families that were not part of the MOSFET, IGBT, and IC training families. The hard part is not just a different random seed. A new seed changes sampled variants, but a new family can change the vocabulary, the local block order, and the exact step labels.

OOD difficulty Why it matters Our defense
New exact strings Official Task 1 is exact-string scored. A model cannot reliably output a string it has never seen or derived. Harvest exact strings from released partial and anomaly inputs; use exact route memory when possible.
New family-specific blocks A hidden family may contain route phases that are not in MOSFET, IGBT, or IC. Use process-rule validation, block-level reasoning, and generated-data fallbacks rather than one family template.
Different optional-step probabilities The correct operation may be predictable, but the exact variant can differ. Use ranked next-step predictions, context backoff, canonical diagnostics, and MBR-style suffix selection.
No visible full-route coupling Route-memory methods are perfect only when the full valid route needed for completion is visible. Report exact-route coverage and calibrated fallback risk instead of hiding the failure mode.

D. The final strategy as an inference cascade

A cascade means we try the strongest, safest evidence first. If that evidence is missing, we fall back to weaker but still measurable methods.

Layer 1: Input audit and vocabulary harvesting

Read every released inference file and collect all step strings. This is crucial for hidden-family exact strings because exact-string scoring cannot reward a string we never emit.

Layer 2: Validator-valid route memory

Run the public validator over full anomaly routes. Keep validator-valid full routes. If a partial sequence is the prefix of one of those full routes, read the next step and suffix directly.

Layer 3: Valid-partial lattice fallback

If no full route exists, compare all visible valid-input partials. When a shorter partial is an exact prefix of a longer partial from the same hidden route, the longer partial reveals the exact next step and a known bridge for completion. This is the main Solution 19 addition.

Layer 4: Paired-length completion guard

If no full route exists, paired 60% and 80% prefixes from the same route constrain the route's total length. Solution 20 uses that only for Task 2 completion fallback. We tested using it for Task 1 reranking, but the 110-family probe showed that optional-step exact strings became less reliable, so the final strategy keeps Task 1 unchanged.

Layer 5: Normalized family-template fallback

If no exact route match exists, normalize family-specific step names into templates such as __FAMILY__ JTE DOSE VERIFICATION. A junior way to think about this is: learn the reusable part of the step string once, then paste in the visible family name at prediction time.

Layer 6: Generated-data and retrieval fallback

If no exact route match exists, use generated valid routes and public training routes to rank likely next steps and suffixes. This is where generated-data prefix/context modeling matters.

Layer 7: Canonical and block-level reasoning

Use canonical operation IDs and block-level process phases to understand whether a prediction is process-plausible even when exact strings differ. These are diagnostics and fallback signals, not official metric replacements.

Layer 7: MBR completion and conformal guard

For completion, choose suffixes that are central under edit-distance-like risk. For reporting, mark whether each row used exact route memory or fallback, and quantify fallback risk.

F. How to interpret the probe

The coupled scenario proves that exact route memory is robust to new strings and new blocks as long as the full valid route is visible. It does not need to "understand" the new string in a semantic way; it can read the exact new string from the matching route.

The no-coupling known-fallback scenario shows the information limit. If the hidden family introduces exact strings that never appear in training or visible inference files, the model cannot reliably output them. Across both hidden families, this is why Top-1 falls to 0.4020 and Task 2 edit distance worsens to 0.5929.

The visible-family-routes scenario is the most important middle case. It has no exact route matches, but it does expose related hidden-family routes. Aggregate Top-1 rises to 0.7625 and Top-3 reaches 1.0000. The per-family Top-1 scores are 0.7775 for THEFOURTHFAMILY and 0.7475 for THEFIFTHFAMILY. This validates our "harvest visible new-family strings and contexts" strategy.

The oracle generator scenario shows what happens if the hidden-family generator architecture is known. Synthetic family-specific training improves fallback performance, but it still does not equal exact route memory because the exact test suffix is not visible. Across both hidden families, oracle-generator Top-1 is 0.7738 with Task 2 edit distance 0.1537.

G. The 110-family scaling curve

We also built a larger synthetic scaling probe with 110 total families. The first 100 families are the training pool. The same last 10 families are always held out for validation. We then train on 2, 5, 10, 20, 40, 60, 80, and 100 families and evaluate on the average of those same 10 validation families each time.

This probe now compares four fallback variants. Raw exact retrieval uses only exact strings seen in training. Template-adapted retrieval learns a placeholder such as __FAMILY__ JTE DOSE VERIFICATION and rewrites it to the visible validation family name. At 100 training families, raw Task 1 Top-1 is 0.6188, while template-adapted Task 1 Top-1 is 0.7688. On the hard slice where the true next step starts with the held-out validation family name, raw Top-1 is 0.0000 and template-adapted Top-1 is 1.0000.

We then added the Solution 19 valid-partial lattice to the same curve. At 100 training families it reaches Task 1 Top-1 0.8938, Task 1 Top-3 1.0000, Task 2 edit distance 0.1066, and Task 2 block accuracy 0.9338. The lattice coverage is 0.5000 because in this probe every route has a 60% and 80% partial, so the shorter half can use a longer visible partial.

Solution 20 adds the paired-length completion guard to the same curve. It deliberately keeps Solution 19's Task 1 ranking, so the 100-family Task 1 Top-1 remains 0.8938 and Top-3 remains 1.0000. The gain is in completion: Task 2 edit distance improves slightly to 0.1065, and Task 2 block accuracy improves to 0.9533. This is why our final pitch calls paired length a completion guard, not a magic next-step predictor.

Solution 21 adds the learned-model bridge needed for the final hybrid strategy. On the same held-out 10-family setup, raw XGBoost gets 10-seed Top-1 0.5806 and has 0.0000 family-specific label coverage. The template-normalized XGBoost bridge gets Top-1 0.7531, Top-3 1.0000, and 1.0000 family-specific label coverage. That is the practical learned-model lesson: train in the transferable __FAMILY__ label space, then rewrite to the visible eval family name.

The curve is useful because it shows the limit clearly. More families help if there is a derivation rule for exact strings. More families do not help raw memorization invent a validation-family exact string that never appeared in training. The full curve page is solutions/many_family_scaling_probe/analysis.html.

H. Final judge-facing claim

Our system is strongest because it separates three cases clearly: exact route evidence available, related OOD family evidence available, and no OOD family evidence available. It is perfect in the first case, strong in the second case, and honest about the information limit in the third case.
